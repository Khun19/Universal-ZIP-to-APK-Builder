# RZ-DEFINE — Request and Change Intake

**Input:** new work request, defect, scope-change proposal, or governance change. **Action:** clarify intended outcome, requester, accountable owner, affected requirements/milestones/baselines, urgency, constraints, dependencies, and whether the request is new work or a controlled change. Identify security and regression impact. **Output:** uniquely identified decision to approve for design, return for clarification, defer, or decline; for a change, an impact/change record. **Evidence:** request source, owner decision/date, affected IDs, risks, scope disposition, and baseline references. **Acceptance:** objective and decision authority are explicit; no implementation begins while material scope is unresolved; a request cannot silently change accepted criteria or reactivate a paused milestone. **Owner:** human scope owner/requestor; technical leads advise. **Status:** use RZ statuses. **Failure:** unclear request returns for clarification; rejected/deferred work is not implemented; an unavailable dependency is BLOCKED with an unblock condition. **Exit:** approved objective/change is traceable and routed to RZ-ARCH/RZ-REQ/RZ-SPEC/RZ-REVIEW as appropriate, or its disposition is recorded closed.

For requirement, architecture, acceptance, scope, dependency, toolchain, prior-PASS, or RZ-governance changes, record reason, affected IDs/milestones, compatibility/security/regression impact, invalidated evidence/gates, owner approval, and new baseline needed. Never use this stage to weaken an observed failing criterion without review.
